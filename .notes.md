# Hacks, cross-workspace seams, and things to watch

Catalog of intentional weirdness in the monorepo so future-you doesn't
"fix" something load-bearing or repeat a workaround badly.


## 1. The `@server/*` path alias has to be declared in three places

Client and shared both follow tRPC types into `apps/server/src/*`. Whichever
workspace is typechecking has to know how to resolve `@server/*` or the
chain breaks (every callback param becomes `any`).

Declared in:
- `apps/server/tsconfig.json`              -> `./src/*`
- `apps/client/tsconfig.app.json`          -> `../server/src/*`
- `packages/shared/tsconfig.json`          -> `../../apps/server/src/*`

If you add a new workspace that imports anything from `@caesar/shared`
or `@caesar/server`, add a matching `@server/*` mapping to its tsconfig.

ESLint pattern bans plain `../../*` imports per workspace (`no-restricted-imports`).
Use `@/` (within the workspace) or `@server/` (cross-workspace) instead.


## 2. Schema lives in shared

`packages/shared/src/db/schema.ts` is the real drizzle schema. All
server code imports it directly as `@caesar/shared/db/schema`. The old
`apps/server/src/db/schema.ts` shim is gone.

When adding a new table:
- Define it in `packages/shared/src/db/schema.ts`.
- Confirm `packages/shared/package.json` exports `./db/schema` (see
  section 3); add it if absent.
- Run `bun db:gen` from `apps/server` to generate migration SQL.
- Migrations stay in `apps/server/src/db/migrations/` (runtime artifact,
  paired with the server data dir).

Drizzle-kit's `--schema` flag in `apps/server/package.json` already
points at the shared location.


## 3. `packages/shared/package.json` has a subpath export you can't comment

```json
"exports": {
  ".": "./src/index.ts",
  "./db/schema": "./src/db/schema.ts",   // <- this one
  "./games/crash": "./src/games/crash.ts",
  ...
}
```

The `./db/schema` entry is what makes `import ... from '@caesar/shared/db/schema'`
resolve. If you add another shared subpath (e.g. moving more code from
server into shared), add it here too.


## 4. Client tsconfig includes server's `declarations.d.ts`

```jsonc
// apps/client/tsconfig.app.json
"include": ["src", "../server/src/declarations.d.ts"]
```

Because client's typecheck follows tRPC types into `apps/server/src/utils/wss.ts`,
which uses the `ws` module augmentation declared there. Without the
include, every `WebSocket.userId` access in server source becomes a type
error in client.

If you add new server-only ambient declarations (e.g. another module
augmentation), be aware client may need them too if they appear on any
type that crosses the boundary.


## 5. `AppRouter` re-export in `packages/shared/src/trpc.ts`

```ts
export type { AppRouter } from '@server/routers';
```

This is a fundamental layering inversion (shared exposes a type defined
by server). It can't be flipped: `AppRouter` is the inferred type of
the server's tRPC router composition, by definition it lives there.
The alias hides the path traversal but the dependency is real.


## 7. Naming conventions to mirror when adding things

- **LocalStorage keys**: `apps/client/src/helpers/storage.ts` enum, prefix `caesar-`.
- **AudioWorklet names**: prefix `caesar-`, processor file + consumer (`audio-gate.ts`)
  must register/load with the exact same string.
- **HTTP cookie**: `caesar-token`. Set in `apps/server/src/http/login.ts`, read in
  `apps/server/src/http/public.ts`. Both sites must match.
- **Container/service**: Dockerfile user, docker-compose service name, Caddy
  reverse_proxy target are all `caesar`. Compose `name: caesar` at top
  pins the project name across hosts.
- **Env vars**: `CAESAR_*` prefix. Declare in `apps/server/src/declarations.d.ts`
  (the `bun.Env` interface). Set defaults in `apps/server/src/utils/env.ts`.
- **Server data dir**: container path `/home/caesar/.config/caesar/`,
  host path `./data` (mounted via docker-compose volume).


## 8. ESLint quirks worth knowing

- `react-hooks/set-state-in-effect` is `error` in client. Genuine
  external-system / form-mirror / state-reset sites carry an inline
  `// eslint-disable-next-line ... -- reason`. If you hit it, either
  add a reason disable or rethink the effect.
- `react-hooks/preserve-manual-memoization` is still `warn`. It flags
  valid `useCallback`/`useMemo` the React Compiler would handle
  itself; not worth blocking CI on.
- `@typescript-eslint/no-explicit-any` is off in `apps/server/src/__tests__/`
  via a flat-config overlay. Test files freely use `any` for mock shapes.
- `unused-imports/no-unused-vars` is `error` across all four workspaces.
  Prefix unused with `_` to silence.


## Summary

### Architecture

```
caesar/
├── apps/
│   ├── client/            React + Vite SPA. Talks to server over tRPC + WS.
│   └── server/            Bun runtime. tRPC router, mediasoup SFU, drizzle/SQLite.
│       └── src/db/        Migrations live here. schema.ts is a shim re-export.
├── packages/
│   ├── shared/            Types, constants, the real drizzle schema.
│   │   └── src/db/        schema.ts (source of truth, drizzle table definitions)
│   └── ui/                React component library consumed by client.
├── caddy/                 Reverse proxy config for prod (HTTPS + WS).
├── docker-compose.yaml    Dev + prod stack definition.
```

Dependency direction is `client/server -> shared -> (nothing)`, with the
one exception that `shared/trpc.ts` re-exports the server's `AppRouter`
type (fundamental, can't be flipped).

### Open refactors worth doing eventually

1. **Fold `useMediaRefs` smaller.** Now that audio analysis moved into
   `SpeakingDetector`, the hook does less than its name suggests; some
   of the remaining ref-juggling could be hooks on their own.
2. **`AppRouter` cross-workspace re-export.** Layering-wise unavoidable
   but worth a brief comment in the trpc client wiring so the next reader
   knows why `@caesar/shared` exposes a server type.
3. **Bare `.select().from(users)` in tests.** Production callsites all
   use explicit field maps now (the only prod offender, `db/publishers.ts`,
   was tightened to `{ id }`). The remaining bare selects live in
   `__tests__/` and don't leak through tRPC, but they will silently
   start returning new columns when the schema grows. Worth tightening
   the next time someone is in those files. Consider a lint rule
   (`no-restricted-syntax` against `.select()` with no argument on
   `users`) to prevent regressions in prod code.
4. **Over-fetch on `getUserById` / `getUserByToken`.** Several callers
   need only `.id` or `.bannerId` but pull the whole `TJoinedUser`
   (avatar/banner joins, social credit subquery, all user columns):
   `change-banner.ts`, `change-avatar.ts`, `wss.ts:83/135/291`,
   `public.ts:89`, `upload.ts:38`, `delete-user.ts:26` (existence check
   only). Not a privacy leak (responses are server-internal or `void`),
   but each call runs three SQL queries (user + roles + social credit
   subquery) where one cheap `.select({ id })` would do. Worth a thin
   `getUserBareById` / `userExistsById` helper.
